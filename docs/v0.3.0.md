# Credlet 0.3.0 rewrite

Development branch: `rewrite/v0.3.0`. Version 0.2.0 remains the published release.

## Required architecture

- A Credlet server written entirely in C, using C libraries for HTTP, cryptography, JSON and storage.
- HTTP transport with application-layer authenticated encryption, as explicitly requested. HTTPS and Vaultwarden are not requirements of this server.
- One Svelte client and one client vault implementation shared by Chrome, Firefox, Android, Linux and Windows.
- Browser extensions are thin browser adapters. Native apps use Tauri and a thin Rust/platform shell. UI and vault logic remain in Svelte/JavaScript.
- MIT first-party code. macOS remains deferred.

The current C implementation uses [Libevent](https://libevent.org/),
[libsodium](https://doc.libsodium.org/), SQLite and json-c. It does not proxy a
Bitwarden API or launch Vaultwarden. The 0.2.0 deployment/client files remain in
the repository for migration reference; they are not part of this runtime.

## Build and run the first working slice

Install a C11 compiler, CMake, pkg-config, libsodium, SQLite, json-c and Libevent
development libraries. Then:

```sh
npm ci
npm run build:server
npm test
npm run build
server/build-v3/credlet-server init --state state-v3 --owner you@example.com
server/build-v3/credlet-server serve --state state-v3 --listen 127.0.0.1 --port 8223
```

`init` prints the server public key and a random, single-use enrollment token.
Transfer both through a trusted channel, such as your server terminal. Install
`extension/dist/chrome` unpacked, or temporarily load the Firefox manifest.
Select **First time? Set up your vault**, enter the HTTP server address, pin
the public key, and enroll with the token and a new master password. Subsequent
clients use the same key and account without an enrollment token.

For a LAN/public server, select an appropriate `--listen` address explicitly.
The default loopback listener is reachable only on the server's machine.
`credlet-server pair --state state-v3` prints the existing public key.
`credlet-server backup --state state-v3 --output /private/path/backup.sqlite3`
creates a consistent SQLite backup without overwriting an existing file.
Restore into a new state directory with
`credlet-server restore --state restored-v3 --input /private/path/backup.sqlite3`.
The restored server keeps its pinned identity and invalidates saved sessions.
Backups include the server identity and authentication data and need private,
encrypted off-host storage.

For Tauri, install its [platform prerequisites](https://v2.tauri.app/start/prerequisites/),
then run `npm run tauri -- dev` or `npm run tauri -- build`. Android additionally
needs the Android SDK/NDK and JDK, `npm run tauri -- android init`, and
`npm run tauri -- android build`. These commands are development paths, not
evidence that all platform packages have passed acceptance.

## Encryption and authentication

1. Installed clients pin the server's Curve25519 public key out of band. No
   server key or executable client is trusted merely because it arrived over
   HTTP. The C server serves no web UI. Svelte is bundled in the installed app
   or extension; the Vite server is for local development only.
2. Each request generates a fresh client keypair and 192-bit random nonce.
   [NaCl authenticated boxes](https://doc.libsodium.org/public-key_cryptography/authenticated_encryption)
   encrypt the operation, account information and session token. The server
   authenticates its encrypted reply using the same keypair relationship.
   JavaScript uses TweetNaCl; C uses libsodium's compatible `crypto_box_easy`.
3. Encrypted messages bind protocol version, request UUID and request/response
   direction. The server enforces a two-minute clock window and persists used
   IDs to reject replay, including across restarts. Incoming bodies, headers,
   JSON depth, authentication attempts and live sessions are bounded.
4. The client derives a root with Argon2id (64 MiB, three iterations, one lane)
   and a random installation salt. HKDF-SHA256 with separate labels produces
   authentication and vault-key wrapping keys. Only the derived authentication
   key reaches the server, inside the encrypted channel. The server stores an
   additional Argon2id verifier and hashes random session tokens at rest.
5. A separate random vault key encrypts complete records using authenticated
   secretboxes. That key is wrapped on the client; it never reaches the server
   unwrapped. Record contexts bind their UUIDs, preventing ciphertext swaps.
   Sessions expire after five minutes. Updates use revision checks; deletions
   leave sync tombstones.

The HTTP channel exposes addresses, timing and ciphertext lengths. This first
channel design has **no forward secrecy** for its transport layer if the
long-term server key is later compromised. Independently encrypted vault
records retain their separate master-password-derived protection. This is a
new application protocol and has not received an independent security review.

## Progress and release gates

Implemented and exercised locally: C server, NaCl JavaScript/C interoperability,
owner enrollment, two-client encrypted sync, revision conflicts, deletion,
consistent backup/restore, pinned-key/tamper/replay rejection, pagination,
interrupted-login locking, and the actual Chrome/Firefox Svelte extension UI.
Five cross-process Node integration tests run against the C server with
AddressSanitizer/UndefinedBehaviorSanitizer; three additional passkey crypto tests
verify signatures independently. The Mozilla linter reports zero errors or
warnings. CI passes for the C server on Linux and Windows and for Tauri debug
builds on both platforms. The actual Linux Tauri UI passes enrollment, editing,
search, TOTP and lock/unlock against the HTTP server. Windows application
acceptance and Android application acceptance remain pending. The Android arm64
debug APK builds in CI. A subsequent Linux UI run exposed an overlapping
status/unlock race; the fix has a cross-process regression test and is awaiting
the next native UI run.
Native Tauri transport is implemented separately
from the UI; it carries only encrypted envelopes over HTTP.

Before a 0.3.0 release, complete and record:

- Repeat the passing Chrome and Firefox website acceptance in release builds:
  password/TOTP filling, foreign-form and ambiguous-field protection, passkey
  creation/sign-in with independent signature verification, wrong-master
  rejection, RP scoping, cancellation, abort and locked-request handling.
- Tauri Linux, Windows and Android builds and actual application execution.
- Native Windows/Linux field filling and Android Autofill/Credential Provider
  integration; the previous Python companion and official Bitwarden Android
  app do not count as implementations of this architecture.
- Password changes, login second factor/recovery, migration decisions, restore
  commands and recovery acceptance. Do not point a new server at 0.2.0 data.
- Extended malformed-input tests,
  lifecycle/lock tests and review of the new protocol.
- Replacement binary/release workflows and current distribution documentation.

There is no published 0.3.0 release yet. The published 0.2.0 acceptance records
describe the earlier architecture and must not be used as evidence for this
rewrite.
